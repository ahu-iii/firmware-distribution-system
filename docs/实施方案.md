# 工业固件安全升级分发系统 实施方案

> 2026-11-05 初版。在线可编辑版本：<https://claude.ai/artifact/1NJqVWkJaLfyH5sdH45Bkz>
> 本文是总体实施思路。具体设计以 [系统设计说明书](系统设计说明书.md) 为准，两者有出入时以设计说明书为准（例如 GCM nonce 的构造方式）。

## 0. 一句话方案

用 **C++17 + Qt 6** 做两个桌面程序（服务端、设备客户端），走**自定义 TCP 二进制协议**（长度前缀分帧 + 心跳 + 断线重连）。通信先做**双向认证握手**（X25519 + RSA-PSS 签名 + HKDF），之后全部 **AES-256-GCM** 加密并带序号防重放。固件包 = **签名清单（manifest）+ 分片镜像**，服务端用 **RSA-3072 私钥（PSS-SHA256）签名**，客户端用预置公钥验签，并做**逐片哈希、整包验签、防降级版本号**检查。设备端用 **A/B 双分区**模拟 Flash，写备用分区、启动失败自动回滚，保证不变砖。服务端 GUI 实时显示每台设备的在线状态、心跳、登录状态、版本和升级进度，并有灰度发布面板和安全告警日志。

## 1. 文档里对本题的要求（逐条对齐）

**本题专项要求（第 3 题）**

| 要求 | 本方案怎么满足 |
|---|---|
| 基于 TCP 分片传输，支持断点续传 | 64KB 分片，客户端持久化下载进度，重连后发 RESUME 从断点继续 |
| 服务端 RSA 私钥签名，客户端公钥验签，失败禁止写 Flash | RSA-3072 PSS-SHA256 签 manifest，manifest 含整镜像和每片的 SHA-256；验签不过直接丢弃并告警 |
| 灰度发布：按设备 ID 分组，先少量后全量 | 发布状态机：草稿 → 灰度 → 观察 → 全量 → 完成，可暂停/终止 |
| 实时上报进度：下载中、校验中、写入中、重启成功/失败 | 客户端状态机 + PROGRESS 消息，服务端表格和进度条实时刷新 |
| fallback：失败后保留旧固件并重启，不变砖 | A/B 双分区 + 启动计数，新分区启动失败自动切回旧分区 |
| 考核：断网恢复后从断点续传 | GUI 提供“模拟断网”按钮，演示进度从 47% 继续 |
| 考核：篡改任意字节必须验签失败并报警 | 篡改 manifest → 签名失败；篡改镜像 → 分片/整包哈希失败（哈希受签名保护），客户端拒写并上报 ALERT，服务端红色告警 |

**所有项目通用要求（第二部分“基础要求”）**

- 严格 C/S，不能用 B/S；代码分**网络层 / 业务层 / 安全层**。
- 必须有可视化界面，**服务端要能看到客户端的心跳、登录状态**，并有详细日志。
- 软件保护**至少选 2 种**：代码混淆、加壳、序列号、许可证文件绑定、程序数字签名。
- 能通过基本渗透测试：**重放、篡改、伪造身份**。
- 交付《系统设计说明书》《通信协议文档》《测试验证报告》。
- 注意两条硬规定：考核时会**随机抽代码让你们逐行解释，讲不清直接 0 分**；**汇报材料禁止用 AI 自动生成**。所以代码要写得朴素、自己能讲清楚，PPT 要自己做。

**评分：五个维度各 20%**：系统设计、网络编程、安全设计、安全实现、对攻击的预判与防范。后两项占 40%，攻击演示要专门准备（见第 8 节）。

## 2. 总体架构

三个程序：

1. **固件签名工具（离线发布端）**：读入原始固件 bin，生成 manifest、计算哈希、用 RSA 私钥签名，输出 `.fwpkg`。私钥只存在这里，用口令加密保存。可以做成服务端里的一个独立窗口，但代码模块要独立，答辩时讲“签名私钥与分发服务分离”是加分点。
2. **分发服务端（GUI）**：设备管理、在线监控、固件库、灰度发布、进度监控、日志告警。
3. **设备客户端（GUI，可多开模拟多台设备）**：认证、心跳、下载、验签、写 A/B 分区、模拟重启、上报状态。

分层架构、模块交互、部署等详细图见 [系统设计说明书 第 3 章](系统设计说明书.md#3-总体架构)。

## 3. 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 语言/构建 | C++17 + CMake | 指定 C++；CMake 跨平台，Windows/Linux 都能编 |
| GUI | Qt 6 Widgets | 表格（QTableView）、进度条、多窗口都现成，标准 C/S 桌面程序 |
| 网络 | Qt Network（QTcpServer / QTcpSocket，非阻塞事件驱动） | 跨平台，事件循环底层就是 select/poll/epoll 多路复用，断线、超时都有信号 |
| 密码 | OpenSSL 3（统一用 EVP 接口） | RSA-PSS、X25519、HKDF、AES-GCM、RAND_bytes 都有，不自己实现算法 |
| JSON | QJsonDocument | 控制类消息和 manifest |
| 存储 | SQLite（Qt SQL 模块） | 设备、发布记录、日志，单文件免部署 |
| 测试 | GoogleTest 或 Qt Test | 帧解析、验签、防降级、续传的单元测试 |
| 打包与保护 | windeployqt + UPX、字符串加密、程序自签名 | 满足软件保护要求（见第 9 节） |

网络层说明：Qt 的 QTcpServer/QTcpSocket 是非阻塞、事件驱动的，答辩时可以讲清它底层就是 IO 多路复用。如果想在“网络编程”这一项多拿分，也可以把服务端网络层换成原生 socket + `select`（Linux 上用 `epoll`），放在独立线程里，再通过 Qt 信号通知界面，接口不变。Windows 上建议用 vcpkg 安装 OpenSSL 和 GoogleTest，Qt 用官方安装器。不要做 Web 前端，会被认为是 B/S。

## 4. 通信协议设计

**帧格式（解决粘包/拆包）**

```
| Magic 'FW' 2B | Ver 1B | Type 1B | Flags 1B | Seq 8B | Length 4B | Body (Length 字节) |
```

- 先读满 17 字节头，再按 Length 读 Body；Length 上限 1MB，超出直接断开（防恶意大包 DoS）。
- 握手完成后 Body 为 AES-256-GCM 密文 + 16 字节标签，**帧头作为 AAD**，所以 Type、Seq 也被认证、不能被改。nonce 由 HKDF 派生的 IV 前缀和 Seq 拼成，详见设计说明书 6.5 节。
- 控制类消息体用 JSON；分片数据用二进制（`chunk_index 4B ‖ data`），避免 base64 膨胀。

**指令集**

| Type | 方向 | 作用 |
|---|---|---|
| HELLO / HELLO_ACK | C↔S | 握手：交换临时公钥、随机数、身份签名 |
| AUTH / AUTH_RESULT | C→S | 设备 ID、当前版本、型号、许可证 |
| HEARTBEAT / ACK | C↔S | 每 5 秒一次，15 秒无心跳判离线 |
| UPDATE_NOTIFY | S→C | 通知有新固件（含 manifest） |
| CHUNK_REQ | C→S | 请求从第 N 片开始（断点续传就是带不同的 N） |
| CHUNK_DATA | S→C | 分片数据 |
| PROGRESS | C→S | 状态 + 百分比 |
| RESULT | C→S | 成功 / 失败原因 / 已回滚 |
| ALERT | C→S | 安全告警（验签失败、降级尝试等） |
| ERROR | 双向 | 错误码 |

状态码、错误码在《通信协议文档》里列成表即可。

## 5. 密码学设计（核心，答辩重点）

### 5.1 密钥体系

| 密钥 | 算法 | 存放 | 用途 |
|---|---|---|---|
| 固件签名密钥 FSK | RSA-3072 | 私钥：签名工具，PKCS#8 + 口令加密；公钥：编进客户端 | 签 manifest，题目明确要求 RSA |
| 服务端身份密钥 | RSA-3072 | 服务端，口令加密 | 握手时证明“我是真服务端”，防中间人 |
| 设备身份密钥 | ECDSA P-256，每台设备一对 | 设备本地加密密钥库；公钥在服务端注册 | 握手时证明“我是合法设备”，防伪造设备 |
| 会话密钥 | X25519 ECDHE → HKDF-SHA256 → AES-256-GCM | 只在内存，断开即清零 | 加密通信，前向安全 |

- 签名密钥和服务端身份密钥**分开**：服务端被攻破也签不出合法固件。
- 所有随机数用 OpenSSL `RAND_bytes`，**禁止 `rand()` / `srand(time(0))`**；**禁止硬编码密钥**（评分表直接点名扣分）。
- 私钥文件用 `PEM_write_PrivateKey` + AES-256 口令加密保存。会话密钥、口令、解出来的私钥用完调用 `OPENSSL_cleanse` 清零，可以封装一个 `SecureBuffer` 类，析构时自动清零（文档也点名了“敏感内存清零”）。

### 5.2 握手（双向认证 + 密钥协商，类似 TLS 1.3 的简化版）

1. C → S：`HELLO{device_id, eph_pub_C, nonce_C, ts}`
2. S → C：`HELLO_ACK{eph_pub_S, nonce_S, Sig_server(transcript)}`，客户端用预置服务端公钥验签，失败即断开（防中间人）。
3. C → S：`AUTH{Sig_device(transcript), 版本, 许可证}`，服务端用注册的设备公钥验签（防伪造设备）。
4. 双方 `HKDF(X25519共享密钥, salt=nonce_C‖nonce_S)` 派生两个方向各自的 AES 密钥。

transcript = 前面所有握手消息的哈希。ts 允许 ±60 秒，nonce 在窗口内缓存，防握手重放。

备选：嫌自研握手风险大，可以直接用 OpenSSL 的 `SSL_CTX`（或 Qt 的 `QSslSocket`）做 **TLS 1.3 双向证书认证（自建 CA）**，上面跑同样的应用层协议。自研的好处是答辩时能讲清每一步，安全设计分更好拿。**（待定，当前按自研设计）**

### 5.3 防重放

- 会话内每帧 Seq 严格递增，接收方记录最后一个 Seq，不是“上一帧 + 1”的直接丢弃并记录“重放攻击”日志。
- Seq 在 AAD 里，被 GCM 认证，改不了。
- 每个会话密钥不同，旧会话抓的包在新会话里解密直接失败。

### 5.4 固件包格式与签名

```
firmware.fwpkg
├── manifest.json        # 被签名的内容
│   { pkg_id, device_model, version: "2.1.0", security_version: 5,
│     image_size, image_sha256, chunk_size: 65536, chunk_sha256: [...],
│     build_time, release_note }
├── manifest.sig         # RSA-PSS-SHA256(manifest.json 原始字节)
└── image.bin            # 固件镜像（可选再 AES-GCM 加密）
```

- 只签 manifest，但 manifest 里有**整镜像和每一片的 SHA-256**，所以镜像任何一个字节被改都会被发现。逐片哈希的好处：下载途中就能发现坏片，只重下这一片。
- 签名直接对 `manifest.json` 的**原始字节**做（OpenSSL `EVP_DigestSign`，PSS 填充）。客户端先对收到的原始字节验签，通过后才用 QJsonDocument 解析，这样不用担心 JSON 序列化前后字节不一致。
- **固件机密性（加分项）**：镜像用每次发布随机生成的 AES-256 密钥加密，该密钥用每台设备的公钥分别包装，防止固件在传输或被截获后被逆向。

### 5.5 客户端验证流程（顺序很重要）

1. 收到 UPDATE_NOTIFY，**先验 manifest 签名**，不通过就不下载，上报 ALERT。
2. 检查型号匹配。
3. **防降级**：`security_version` 必须 ≥ 本地保存的最小安全版本，且 version 比当前新。防止攻击者重放一个“合法签名但有漏洞的老固件”。
4. 下载，每片校验 SHA-256，坏片重下（同一片连续失败 3 次判定为攻击，告警并中止）。
5. 下载完：计算整镜像 SHA-256 与 manifest 比对，并**再次验签**，全部通过才进入写入。
6. 任一步失败：**不写 Flash**，删除临时文件，状态 FAILED，上报 ALERT（原因 + 哈希值），服务端界面红色告警并写审计日志。

### 5.6 审计日志防篡改

每条日志带 `prev_hash`，本条 `hash = SHA256(prev_hash ‖ 内容)`，形成哈希链，并定期用服务端私钥对链头签名作为检查点。界面提供“校验日志完整性”按钮，改任何一条都能定位出来。这项在评分表“审计日志的取证价值”里。

## 6. 业务功能设计

### 6.1 断点续传

- 客户端在 `download/` 下存 `pkg_id.part` 和 `pkg_id.state.json`（已完成分片的位图 + manifest 哈希）。
- 断线后指数退避重连（1, 2, 4, 8 秒…，上限 30 秒），重新握手认证，然后发 `CHUNK_REQ{pkg_id, from_index=N}`。
- 恢复时先重新校验已下载部分的哈希，防止本地临时文件被篡改。
- 演示：客户端界面“模拟断网”按钮直接关 socket；或者在中间加一个小 TCP 代理，可以随时掐断（这个代理还能复用来做中间人篡改演示）。

### 6.2 灰度发布

- 设备分组：按设备 ID 打标签，例如 `canary`（2 台）、`line-A`、`line-B`，也支持手动勾选设备 ID。
- 发布状态机：`草稿 → 灰度中 → 观察期 → 全量推送 → 完成`，另有 `已暂停` 和 `已终止`。
- 灰度批次全部成功（重启后上报新版本且心跳正常持续 N 秒）才允许点“全量推送”；失败率超过阈值（比如 > 0）自动暂停并告警。
- 控制并发：全量时每次最多同时推送 K 台，防止服务端带宽被打满。

### 6.3 设备状态机与进度上报

`IDLE → NOTIFIED → DOWNLOADING(%) → VERIFYING → WRITING(%) → REBOOTING → SUCCESS`

失败分支：`FAILED(原因)`、`ROLLED_BACK`。每次状态变化及下载每 5% 发一条 PROGRESS。

### 6.4 A/B 分区与 fallback（不变砖）

设备本地目录模拟 Flash：

```
device_<id>/
├── slot_a/firmware.bin   # 当前运行
├── slot_b/firmware.bin   # 新固件写这里
└── boot.json             # {active:"a", pending:"b", boot_attempts:0, min_security_version:5}
```

1. 新固件只写**非活动分区**，旧分区完全不动，写入中途断电也无影响。
2. 写完设置 `pending=b` 并“重启”（客户端程序自我重启或界面模拟重启动画）。
3. 模拟 Bootloader 启动前**再验一次 slot_b 签名**（安全启动），然后运行“自检”。
4. 自检通过：`active=b`，更新 `min_security_version`，上报 SUCCESS。
5. 自检失败或连续启动 3 次失败：切回 `slot_a`，上报 ROLLED_BACK。
6. 演示用：可以准备一个“签名合法但自检会失败”的固件（镜像里带一个 `selftest=fail` 标志），专门演示回滚。

## 7. 界面设计

**服务端**

- 设备监控表：设备 ID、IP、在线/离线、登录状态、最后心跳时间、当前版本、升级状态、进度条（文档明确要求能看到心跳和登录状态）。
- 固件库：导入 `.fwpkg`，展示 manifest 和验签结果。
- 灰度发布：选固件、选分组、开始灰度、全量、暂停。
- 日志与告警：普通日志、安全告警（红色）、日志完整性校验按钮。

**客户端**：设备信息、当前版本、A/B 分区状态、升级进度条、本地日志，以及演示按钮（模拟断网、模拟断电、切换攻击模式）。

## 8. 攻击演示与测试（占 40% 分数，务必准备）

| 攻击 | 演示方法 | 预期结果 |
|---|---|---|
| 篡改固件任意字节 | 用十六进制编辑器改 `.fwpkg`，或让中间代理翻转一个比特 | 验签/哈希失败，拒写 Flash，服务端红色告警 |
| 伪造固件 | 用攻击者自己生成的 RSA 私钥签名 | 验签失败 |
| 降级攻击 | 推送一个签名合法的旧版本 | 被 security_version 拦截 |
| 报文重放 | 抓一个包原样再发 | Seq 检查拒绝并记录 |
| 中间人 | 中间代理替换握手公钥 | 服务端签名验证失败，断开 |
| 伪造设备 | 用未注册的设备 ID 或错误私钥接入 | 认证失败，记录日志 |
| 抓包看明文 | Wireshark | 只能看到密文 |
| DoS | 大量连接、超大 Length、慢速连接 | 单 IP 连接数限制、帧长上限、握手超时断开 |
| 断网 | 下载中掐断 | 重连后从断点续传 |
| 写入时断电 | 写入中杀进程 | 下次启动仍从旧分区启动 |

建议写一个 `attack_tools/` 目录放这些脚本，测试报告里每项附截图和日志。

## 9. 软件保护（至少选 2 种）

推荐 3 种，和本题业务结合最自然：

1. **数字签名基础**：签名工具给 `client.exe` 生成 `client.exe.sig`，客户端启动时用内置公钥校验自身文件，被改过就拒绝运行。和固件签名是同一个思路，好讲。
2. **许可证文件绑定**：服务端给每台设备签发 `device.lic`（设备 ID + 硬件指纹哈希 + 有效期 + RSA 签名），硬件指纹可以取网卡 MAC + 磁盘序列号的哈希，客户端启动时校验，拷到别的机器无效。
3. **加壳 + 字符串加密**：Release 版用 UPX 加壳；敏感字符串（公钥指纹、关键提示）用编译期 XOR 加密的模板/宏处理，反编译看不到明文。有余力可以试 OLLVM 的控制流平坦化。答辩时用 IDA 或 Ghidra 展示加壳前后的对比。

## 12. 容易踩的坑

- 先下载完再验签：错，应该先验 manifest 签名再下载，避免浪费带宽和处理恶意数据。
- 只做哈希不签名：哈希攻击者可以一起改，必须由签名保护哈希。
- 用 RSA PKCS#1 v1.5 加密或 ECB 模式：用 PSS 签名、OAEP 加密、GCM 模式。
- GCM nonce 重复：每帧 nonce 必须唯一，绝不能复用。
- AES-GCM 解密后**必须检查 `EVP_DecryptFinal_ex` 的返回值**，认证标签不对就丢弃整帧。
- 私钥写在代码或明文配置里：评分表点名扣分。
- 帧头的 Length 不校验就分配内存或拷贝：典型缓冲区溢出，评分表点名。一律先检查上限，用 `QByteArray` / `std::vector`，不要往固定大小数组里 `memcpy`。
- OpenSSL 对象（`EVP_PKEY`、`EVP_MD_CTX` 等）用 `std::unique_ptr` 加自定义删除器管理，避免泄漏；不要用已废弃的 `RSA_*` 低层接口，统一用 EVP。
- 在 GUI 线程里做大文件哈希和写盘：界面会卡死，放到 QThread，用信号更新界面。
- 交付前跑一遍 cppcheck 或 clang-tidy，“静态扫描无高危漏洞”是课程的自检点。
- 只演示正常流程：攻击演示和日志是 40% 的分。
