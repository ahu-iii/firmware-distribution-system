## 0. 怎么讲

被抽到一段代码时，按四句话回答，每段不超过一分钟：

1. **这段做什么**：一句话，用业务语言（“设备收到一帧数据，先看帧头再决定要不要收 Body”）。
2. **逐行**：按代码顺序讲关键行，变量名照念，说清楚每个判断挡住的是什么情况。
3. **为什么这样写**：不这样写会出什么问题（攻击或故障），对应哪条红线或检查项。
4. **怎么验证的**：对应的单元测试或用例编号（UT、FT、ST），证据在哪。

不会的时候说“这一段是对方写的，我理解的是……”，比硬编好。

## 2. A 主讲

### A1 帧解码：Length 先校验再分配内存

位置：`common/frame_codec.cpp` `FrameDecoder::next`。帧头 16 字节：Magic 2（`FW`）+ 版本 1 + 类型 1 + 序号 8 + Length 4，大端。

逐段要点：

1. 缓冲里不足 16 字节就返回 `NeedMore`，等下一批数据（半包）。
2. 只看帧头：Magic 不对 → `BadMagic`；版本不对 → `BadVersion`；读出 Length 后**立即和 `maxBody_` 比较**，超过 → `FrameTooLarge`。这一步还没有为 Body 分配任何内存。
3. 出错时清空缓冲、记住错误，之后 `feed` 和 `next` 都直接返回错误，上层发 ERROR 帧后断开。
4. Body 没收齐继续 `NeedMore`；收齐后用 `mid` 取出一帧，`pos_` 前移。调用方循环调用 `next()` 就能处理一次收到多帧（粘包）。
5. 已消费部分超过 64 KB 才整理缓冲，避免每帧都搬内存。

常见追问：

- **为什么一定要先判 Length？** 对端可以在帧头里写 4 GB，如果先按 Length 分配再判断，一个连接就能把服务端内存打满。`maxBody_` 来自配置 `max_frame_body`，上限 1 MB，配置加载时还检查不能超过 1 MB、不能小于一片固件加帧开销。
- **超长帧为什么不是跳过而是断开？** 帧边界已经不可信，后面的字节无法再对齐，只能断开。
- 测试：`FrameCodec.*` 单元测试（超长、错 Magic、半包、粘包、逐字节喂入），ET-01 非法帧注入。

### A2 帧序号与收包循环

位置：`common/net/frame_channel.cpp` `FrameChannel::onReadyRead`。

1. 每次最多读 `kReadChunk` 字节喂给解码器，不一次读完整个 socket 缓冲。
2. 每取出一帧检查 `frame.seq == recvSeq_ + 1`：序号必须从 1 开始逐个加 1，否则回 `SeqError` 并断开。
3. 解码出错同样发 ERROR 帧、优雅关闭（`closeGracefully` 先把发送缓冲发完，超时再强制 `abort`）。

追问：

- **TLS 已经防重放了，为什么还要帧序号？** TLS 防的是记录层重放；帧序号防的是应用层把同一帧再发一次（例如有缺陷的客户端或中间件重发）。两层各管一层，ST-08 两种都测了。
- **登录请求被录下来重放呢？** 每个连接是新的 TLS 会话，录下来的密文解不开；明文层面 LOGIN 带时间戳，超出窗口（默认 ±60 秒）拒绝（见 A3）。

### A3 设备登录裁决

位置：`server/business/login_handler.cpp` `LoginHandler::handle`。到这里时 TLS 握手和证书校验已经通过。

按顺序五道检查，任何一道不过就拒绝：

1. JSON 格式和必填字段（`device_id`、`ts`）→ `1005`。
2. 时间戳窗口：`|now - ts| > login_ts_window_ms` → `2002`，挡住录下来稍后重放的 LOGIN，也挡住时钟偏差太大的设备（FT-22）。
3. **上下文绑定**：LOGIN 里自报的 `device_id` 必须等于 TLS 握手时出示的证书名称（`peer.name`），否则持有 DEV-002 证书的设备可以自称 DEV-001 → `2007`。
4. 注册表：已注册、未停用、证书指纹与注册时绑定的一致。三种失败对设备都只回 `2005`，不告诉对方差在哪；详细原因只写服务端日志和告警。
5. 许可证验签（`2006`），然后查失败锁定（同一设备 ID 或同一 IP 窗口内失败 5 次锁定）。

全部通过后登记在线，回 `event_ack`（该设备已连续收到的最大事件序号）；设备报来的 `event_base` 比它大时先对账（A6）。

追问：

- **为什么失败锁定放在最后？** 材料不对的请求在前面就被拒并计数；锁定期内即使材料全对也不放行，所以放在“全部检查通过之后、放行之前”。
- **为什么 2005 不细分？** 防探测：攻击者不能通过错误码区分“没注册”和“被停用”。

### A4 灰度发布互锁与紧急停止

位置：`server/business/rollout_manager.cpp`。状态机：草稿 → 灰度中 → 观察期 → 待确认全量 → 全量推送中 → 已完成；失败、告警、开关被关、服务端重启 → 已暂停；紧急停止、终止 → 已终止。

- `checkModelFree`（互锁 ①）：同一型号同时只能有一个发布处于推送阶段，**已暂停的也算**，因为它随时可能被继续。
- `checkDevice`（互锁 ②）：设备已注册、未停用、在线（离线不缓存、不盲发）；型号一致；不在下载到重启之间；刚下发过、还没在心跳里报出新状态的（两个心跳间隔内）也不推。
- `evaluate`：金丝雀有失败且还有全量批 → 自动暂停；金丝雀全部有结果 → 没有全量批（单台下发）就“已完成”，有全量批就进观察期，观察期到了由 `finishObservation` 检查是否稳定。全量阶段失败比例超过阈值自动暂停。
- `abort`：① 正在升级的设备发 `UPDATE_CANCEL`；② 还没推的记为“已取消”；③ 发布记为“已终止”。紧急停止只能用于推送中的发布，草稿和已暂停的用“终止”（要输口令）。

追问：

- **紧急停止时设备正在写 Flash 怎么办？** 写入前收到取消的设备放弃升级、保留旧固件；已经在写的照常写完、重启、自检，A/B 保证它要么转正、要么回滚，不会停在半截（ST-26）。
- **谁能做这些操作？** 改数据的函数都是私有的，只有 `AdminService` 先查角色、再核对口令后才能调用；紧急停止不要求口令（越快越好），但要求操作员或维护员角色。

### A5 分片服务

位置：`server/business/chunk_service.cpp` `handleChunkRequest`。

1. 格式不对回 `1005`，不断开。
2. **只能要下发给自己的那个包**：设备 ID 取自这条会话（登录时已和证书核对），不是请求里自报的。刚被取消的包的迟到请求是正常的先后顺序，不记安全事件（BUG-003 修复）。
3. 范围：`1 ≤ count ≤ 窗口上限`，`from_index + count` 不超过总片数——用减法比较，避免加法溢出。
4. 流控：上一批还积压在发送缓冲里就不再发，不停要却不收的连接最多让服务端缓存两个窗口。
5. 按偏移从 `.fwpkg` 读片发送；文件被截断了就不发残缺的分片。

### A6 事件入库与对账

位置：`server/business/event_store.cpp`。数据库主键 `(device_id, event_seq)`，`device.event_ack` 记每台设备已连续收到的最大序号。

- `accept`：① 格式；② `seq ≤ event_ack` 是重复（补传时正常会遇到），不入库；③ 超前太多（> 1000）不入库；④ `INSERT OR IGNORE` 入库并在**同一个事务**里推进 `event_ack`，要么都写进去，要么都没写。
- `advance`：从 `event_ack` 往后找连续的序号，缺了下一个就停，后面的先“暂存”等补齐——保证交给业务（发布推进、告警）的顺序和设备产生的顺序一致。
- `reconcileOnLogin`：设备说“我已确认删到 `event_base`”，服务端却只收到 `event_ack`（例如数据库从备份恢复过），中间那段两边都没有了：告警并跳过，否则设备永远等不到确认。
- `finish`：事务提交之后才更新内存、通知业务：**先落库、后处理**。

追问：**为什么不丢、不重、不乱序？** 不丢靠设备 outbox 落盘加确认后才删（B8）；不重靠主键加 `seq ≤ ack` 判重；不乱序靠 `advance` 只放行连续序号。FT-09 的证据是服务端 77 行、序号 1 ~ 77、无重复。

### A7 审计哈希链

位置：`server/security/audit_service.cpp`。

- `computeHash`：`hash = SHA-256(prev_hash ‖ JSON 数组[id, ts, level, category, actor, source, device_id, message])`。用 JSON 数组是因为每个字段都有引号和分隔符，字段内容里出现什么字符都不会和相邻字段混淆（不能简单拼接）。
- `append`：序号自己分配并参与哈希；空字符串统一成 `""`（Qt 会把空 QString 绑成 NULL，违反 NOT NULL）；每 100 条和程序退出时写检查点文件。
- `verify`：逐行检查 ① 序号从 1 连续（删中间一条会断号）；② `prev_hash` 等于上一行的 `hash`；③ 用本行内容重算 `hash`；最后和检查点比对（删掉末尾几条会和检查点对不上）。

追问：**数据库管理员把整条链都重算一遍呢？** 那样链本身是自洽的，但和单独存放的检查点（可以放只读备份目录）对不上；检查点的作用就在这里，设计文档第 13 章写了这一点。

## 3. B 主讲

### B1 TLS 配置

位置：`common/security/tls_channel.cpp`。

`load`（加载材料时）：

1. 只认 Qt 的 OpenSSL 后端：Windows 的 Schannel、macOS 的 Secure Transport 不支持“只开一个套件、只用 X25519”，找不到 OpenSSL 时宁可不启动网络，也不降级。
2. Qt 加载的 OpenSSL 和本程序用的大版本必须一致且 ≥ 3（一个进程里混两版 libcrypto 会崩）。
3. 本端证书和私钥用 `X509_check_private_key` 确认是一对，证书在有效期内。
4. 私钥 PKCS#8 明文临时转 PEM 交给 `QSslKey`，交完立刻 `OPENSSL_cleanse` 清零。

`prepare`（每个连接）：

- `setProtocol(QSsl::TlsV1_3)`：只允许 TLS 1.3。
- `setCiphers({cipher_})`：只启用 `TLS_AES_256_GCM_SHA384` 一个套件（带认证加密，红线 1-4）。
- `setEllipticCurves(X25519)`：密钥交换只用 X25519 临时密钥，前向安全。
- `setPeerVerifyMode(VerifyPeer)`：**双向认证**，两端都必须出示证书；`setPeerVerifyDepth(1)`：链上只有叶子和根。
- `setCaCertificates({caCert_})`：信任库只有自建 CA，系统证书库里的任何 CA 都不信任。
- 关闭会话票据、会话复用和压缩：每次连接完整握手，没有 0-RTT 重放面。
- `sslErrors` 只记日志，**全项目没有任何一处调用 `ignoreSslErrors()`**（红线“不为调试关闭证书校验”）。

`verifyPeer`（握手后复查）：再确认协议是 TLS 1.3、套件是指定的那个，然后用 `CertVerifier` 做完整校验（B2）；CRL 文件变了就先重新加载。

追问：**为什么握手后还要复查版本和套件？** 防御纵深：即使有人改了配置或 Qt 行为变化，也不会在别的版本或套件上收发业务数据。

### B2 证书完整校验

位置：`common/security/cert_verifier.cpp` `CertVerifier::verify`。

1. 证书能解析；CA 和 CRL 已加载。
2. 用途：服务端证书必须有 `serverAuth`，设备证书必须有 `clientAuth`——两种证书出自同一个 CA，这一项挡住“拿设备证书冒充服务端”。
3. 名称：校验服务端证书时按 IP（`set1_ip_asc`）或主机名（`set1_host`）比对 SAN。
4. `X509_verify_cert` 一次完成：链到自建 CA、签名、有效期、用途、名称、CRL 签名与吊销状态。
5. 再查有效期上限：叶子证书超过 90 天直接拒绝（根证书 365 天，在 `loadCa` 里查）。
6. 设备证书的 CN 承载设备 ID，后面登录时和 LOGIN 里的 ID 比对（A3）。

追问：**CRL 怎么生效？** 签发工具 `revoke` 后把新的 `crl.pem` 覆盖到配置的位置，服务端下一次握手前发现文件变了就重新加载；序号比当前小的 CRL 拒绝加载，防止用旧 CRL 把已吊销的证书“恢复”（ST-04）。

### B3 manifest 先验签后解析，下载前三项检查

- `ManifestVerifier::verify`：**第一步验 RSA-3072-PSS 签名**，不过直接返回，后面的 JSON 解析根本不执行；签名过了，说明字节出自 FSK，才交给解析器。顺序反过来的话，攻击者构造的畸形 JSON 会先进解析器（攻击面）。
- `UpdateValidator::check`：① 验签；② 型号——型号写在受签名保护的 manifest 里，没法把别的型号的固件改成本型号；③ 防降级。三项都过才把 manifest 交给调用方（`verified` 是局部变量）。
- `DeviceAntiRollback::allows`：安全版本号低于本机最小值拒绝（等于可以，同一安全级别的功能更新）；版本号必须比正在运行的新。版本号无法解析按拒绝处理。

追问：

- **公钥从哪来，被换了怎么办？** FSK 公钥文件随设备出厂，配置里写着它的 SHA-256 指纹，启动时 `loadPinnedFskPublicKey` 核对，对不上不运行。
- **为什么是 PSS 不是 PKCS#1 v1.5？** PSS 有随机盐、有安全性证明，是新设计推荐的 RSA 签名填充；用的是 OpenSSL EVP 接口，没有自己实现算法。

### B4 逐片校验与写入前复验

- `Downloader::onChunkData`：只接受“当前包、当前窗口、还没完成”的分片；长度和 SHA-256 都与已验签 manifest 一致才写盘；不符不写盘，仍算缺失，下次重要；同一片连续 3 次不符中止并告警（`3004`）。写盘失败（磁盘满）删掉下了一半的文件把空间还回去（BUG-008）。
- `Updater::onDownloadCompleted` / `verifyStep`：分片下载时校验过，但文件在磁盘上躺着可能被改，所以**写 Flash 前把整个镜像从头再算一遍**，并且再验一次签名、确认验出来的还是同一份 manifest（比对 `imageSha256`）。不过就删临时文件、告警（`3005`），不写入。分步执行（每步 1 MB），界面不卡。

### B5 A/B 分区写入与 Bootloader 回滚

写入（`client/business/updater.cpp`）：

- `startWriting`：目标是**非活动分区** `otherSlot(active)`，正在运行的分区从头到尾不碰，写到一半断电也还能从它启动。
- `commitWrite`：① 镜像刷盘，写 manifest 和签名；② **最后一步**才在 `boot.json` 里登记 `pending`——在这之前断电，`boot.json` 没有 pending，下次仍从旧分区启动；③ 模拟重启。

启动（`client/business/bootloader.cpp` `boot`）：

1. 有待确认的新固件：**先把启动次数加 1 并存盘，再去验**——即使新固件一启动就死机断电，次数也在涨，超过 3 次就不再试它。
2. `checkSlot` 五项：验签 → 型号 → 安全版本号不低于下限 → 镜像长度、逐片哈希、整镜像哈希 → 自检。
3. 通过就转正：活动分区切过去，清 pending，**这时才**提升最小安全版本号。如果提前提升，回滚时旧固件的安全版本号低于下限，反而启动不了。
4. 不通过就回滚：只清掉 pending，旧分区本来就没动过；结果上报 `ROLLED_BACK`（`3007` 自检失败）。
5. 活动分区也启动不了时试另一个分区（要过自检）；都不行进入恢复模式，等服务端推送，界面明确提示，不会误认为变砖。

追问：**`boot.json` 写到一半断电？** 用临时文件写完、刷盘后改名替换（原子写），断电只会留下完整的旧文件或完整的新文件；内容不合规只可能是被人改了，按第一次上电处理并记安全日志。

### B6 口令慢派生与账号锁定

- `pbkdf2Sha256`（`common/crypto/kdf.cpp`）：直接调 OpenSSL 的 `PKCS5_PBKDF2_HMAC`，摘要 SHA-256，不自己实现。
- `OperatorAuth::createAccount`：口令规则（10 ~ 128 字节，含字母和数字）→ **每个账号 16 字节随机盐**（两个账号口令相同，存下来的也不同）→ 60 万次派生出 32 字节 → 存 `kdf` 名、迭代次数、盐、派生结果。数据库里没有口令原文，也没有一次 SHA-256。
- `OperatorAuth::verify`：
  - 账号不存在也照样派生一次，让“账号不存在”和“口令不对”耗时相近，防按响应时间探测账号名；
  - 锁定期内直接拒绝，不派生、不计数；
  - 表里的派生函数名、迭代次数（< 10 万）、哈希长度被人改过，一律按口令错误处理（防降级攻击）；
  - 用 `CRYPTO_memcmp` 常数时间比较；
  - 连续错 5 次锁 10 分钟；计数写不进数据库就不放行（否则锁定形同虚设）。
- 口令在内存里用 `SecureBuffer`，析构时 `OPENSSL_cleanse` 清零。

追问：**为什么 60 万次？** 参照 OWASP 对 PBKDF2-HMAC-SHA256 的建议值；登录一次约几百毫秒，人感觉不到，暴力破解成本按次数线性增加。

### B7 私钥文件 AES-256-GCM 封装

位置：`common/crypto/key_file.cpp`。文件格式：魔数、版本、KDF 编号、迭代次数、16 字节盐、12 字节 nonce、密文长度（这些是文件头）+ 密文 + 16 字节 GCM 标签。

- `sealPrivateKey`：每次新生成盐和 nonce（同一把私钥同一个口令封装两次，文件也完全不同）；口令经 PBKDF2 派生 256 位密钥；**整个文件头作为 AAD** 参与 GCM 认证，改迭代次数、改盐都会让解密失败。
- `openPrivateKey`：先把文件头每个字段查一遍（魔数、版本、迭代次数范围、长度字段和文件实际长度一致）才开始做昂贵的派生；解密失败统一提示“口令错误或文件被改动”。

追问：

- **为什么不用 OpenSSL 默认的 PEM 加密？** 那是 CBC 模式，没有完整性保护，红线明确禁止；GCM 是带认证的加密。
- **口令从哪来？** 部署时注入：环境变量 `FWDS_KEY_PASSPHRASE`，程序读取后立即清除并抹掉进程环境块里的值（BUG-001）；macOS 存登录钥匙串，Windows 用 DPAPI。不写配置、不进仓库。

### B8 事件 outbox：先落盘再发送

位置：`client/business/event_outbox.cpp`。文件 `outbox/events.jsonl`（一行一个未确认事件）和 `outbox/seq`（最近分配的序号）。

- `record`：分配序号 `lastSeq_ + 1`，加毫秒时间戳 → **先追加一行并刷盘**（`appendLine` 里 `syncToDisk`）→ 成功后才更新序号、放进内存队列 → 在线才发送。落盘失败就不发送：发出去却没落盘的事件，断电后会被同一个序号的新事件顶掉。
- `onLoggedIn`：服务端在登录结果里告诉“已连续收到第几号”（`event_ack`），先删掉已确认的，剩下的按序号从小到大补传；如果服务端的序号比本地还大（本地数据目录被清过），接着服务端的序号重新编号，否则会被当成重复丢掉。
- `applyAck`：确认后才删除，整个文件用 `QSaveFile` 写临时文件再改名替换，重写途中断电留下的是完整的旧文件。
- `open`：启动时读回未确认事件；追加到一半断电留下的半行丢掉——那个事件没刷盘完成、没发送过，`seq` 文件也没记下它，下一个事件会重用这个序号，服务端看到的序号仍然连续。

追问：**断网好几天会不会撑爆？** 事件只在升级过程中产生（每个阶段一条、下载和写入进度每 5% 一条），一次升级几十条，几天也只有几百行。服务端最多接受超前 1000 个序号的事件；落盘失败的事件不发送，记错误日志。
